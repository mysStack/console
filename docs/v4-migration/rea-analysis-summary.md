# REA 阶段分析总结

> 文档用途：作为 V4 迁移各阶段进入正式开发前的分析门禁记录。  
> 统一顺序：`Pn-REA → Pn-DEV → Pn-VERIFY → Pn-PR`。  
> 当前结论：本轮从 P0-REA 重新开始，P0-REA 分析中，P1-REA 未开始，P2-REA 未开始（历史先行证据）；不得据此进入新的正式模块开发。

## 1. 门禁规则

每个阶段必须先形成可复核的分析文档，再开始该阶段正式实现。分析文档至少要记录：

- 分析对象的版本、分支、提交或制品摘要；
- 旧 V3 源码、构建产物和实际运行时证据的来源；
- 路由、页面、API、Action、Store、权限、缓存、作用域和异常行为；
- 每条结论的证据类型：源码、REA 静态分析、运行时观察、Network、测试或推断；
- 已确认行为、未确认行为、冲突证据和剩余未知项；
- 对应的 V4 文件、可复用部分、需要改造部分和不能直接迁移的部分；
- 进入开发的前置条件、复核人和门禁结论。

只有“未解决的高风险未知项已关闭或明确隔离”，并且矩阵、证据和结论完成复核，阶段才可以从 `分析中` 进入 `开发中`。

REA 不要求对整个大型 Bundle 取得无截断的语义图；门禁要求是所有当前启用的路由、模块、扩展和动态 Action 都有可追溯的分析覆盖，剩余未知项有影响评估、验证方法和关闭条件。没有覆盖的部分必须明确标记为未知，不能用“全量分析已完成”概括。

证据具有版本边界：源代码 commit、制品 tag/digest、部署 Pod imageID 或运行时环境发生变化后，旧证据只能保留为历史记录，必须重新核对受影响结论。

阶段状态词义统一如下：

- `未开始`：尚未形成该阶段的正式分析或实现入口。
- `分析中`：已开始收集证据，但分析覆盖、未知项或关闭条件尚未完成。
- `待复核`：分析交付物已经形成，等待指定复核人确认门禁结论。
- `已通过`：指定复核人已确认门禁通过，可以进入下一阶段。
- `不通过`：仅在指定复核人完成正式复核后使用，表示交付物未满足门禁，需要返工。
- `阻塞`：存在当前无法由本阶段继续工作解除的外部条件；必须记录阻塞责任、解除条件和下一次复核时间。

“先行证据”不是阶段状态。历史实现、测试或部署可以附在阶段记录中，但不能替代 `REA` 门禁。本轮从 P0-REA 重新开始，历史先行证据不作为当前执行入口、完成度或风险结论。正式门禁必须由项目负责人或其指定复核人确认，不能由执行者自行宣布通过。

表格中“分析中（本轮重新开始）”和“未开始（历史先行证据）”的括号内容只是补充说明，不是新增状态值；正式状态仍分别是 `分析中` 和 `未开始`。

### 3.2 已观察结果

- 目录中共有 1,451 个候选文件；REA 摘要检查了 563 个文件。
- 识别到 440 个相关文件，解析了 434 个 JavaScript 文件。
- 读取文本约 28,741,771 字节，未发现 UTF-8 解析失败。
- 访问 AST 节点 5,134,695 个，记录 4,353 个静态发现。
- REA 明确将 JavaScript/HTML 按静态文本解析，没有执行 Bundle 启动代码。
- 当前结果可以证明该制品的身份和静态分析范围，不能单独证明页面运行时的完整路由、Network、Action 或权限行为。

### 3.3 覆盖限制和未知项

本轮结果的 application graph 和 semantic graph 均为 partial：

- application unknowns：842；
- semantic unknowns：98,907；
- semantic graph 因结果容量限制被截断；
- 许多大型 Chunk 只保留了静态文件事实，未完成语义图分析；
- REA 返回 848 项限制，其中 839 项在摘要中省略，完整限制仍保留在父证据；
- 本轮没有执行浏览器运行时观察，也没有把具体 ConfigMap、Secret、ServiceAccount 行为与制品中的 Chunk 建立完整对应关系。

因此，本轮只能作为 P0-REA 的第一轮制品基线，不能作为 P0-REA 通过结论。

本轮结果的正确用途是定位后续 focused REA 的入口，不是把 44 MB 制品的一次摘要分析当作所有功能已经分析完成。后续 focused REA 必须把每个结论回链到具体 Chunk、V4 文件或运行时证据。

## 4. 旧 V3 源码基线

当前工作区和 `/home/bruce/code` 的有限目录扫描没有找到名为 `kse-console-v3` 的独立源码目录，但同一 Git 仓库的远程发布引用中保留了 V3 源码候选：`origin/release-3.2`（`5e6b2d05361fc8bd70b04e900a914b399deae7a8`）、`origin/release-3.3`（`cd90e5b64326df76432a9cafb05c2a08aa40ecdf`）和 `origin/release-3.4`（`175710fefeeba6ff295c2c0967b4d45b83563d26`）。三个分支的 `package.json` 均声明版本 `3.0.0`、许可证 `AGPL-3.0`，并含 `src/actions/configmap.js`、`src/actions/serviceaccount.js` 等旧实现。

这不是“旧源码不存在”的结论。当前可以把 `origin/release-3.4` 作为最新 V3 源码参考，但还没有把它与 `v3dist` 的构建产物建立可核验的对应关系。P0-REA 仍需：

1. 固定采用的旧 V3 源码引用和对应 commit；
2. 核对旧源码的构建配置、依赖锁定文件和制品生成时间；
3. 将旧源码 commit 与当前 `v3dist` 制品版本建立对应关系；
4. 如果无法建立对应关系，必须明确“源码候选已定位但制品来源未知”的边界，不能把 Chunk 反推成原始 TSX。

## 6. 当前门禁结论

- P0-REA：**分析中（本轮重新开始）**。已有静态依赖清单、旧 V3 源码候选和第一轮 `v3dist` REA，但制品代次、完整 Chunk 语义分析、运行时入口和扩展/Action 盘点仍不完整；对应未知项见 `P0-U001`～`P0-U004`。旧源码定位是分析交付项，不把上一轮实现当作当前风险结论。
