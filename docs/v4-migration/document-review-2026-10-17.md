# V4 迁移文档与流程复核记录

> 复核日期：2026-10-17（上海时间）  
> 复核范围：`console-v4-migration-plan.md`、`console/docs/v4-migration/*.md`、当前 `console` 分支和远程分支元数据。  
> 复核目的：确认阶段顺序、REA 门禁、证据链、状态字段和验收标准没有互相冲突或遗漏。

## 1. 复核结论

流程方向已经正确：每个阶段必须按：

```text
Pn-REA → Pn-DEV → Pn-VERIFY → Pn-PR
```

但原文档还有几处会让执行者误以为可以提前开发或把历史测试当作正式验收。本次已经修正这些问题：

- 删除 Deployment“首个试点”与第 12 节 P2 先行顺序之间的冲突；
- 把矩阵中混入 P2 先行实现的 P0 完成项拆开；
- 把 Deployment 配置引用的“测试中”改为“分析中”，避免绕过 P3-REA；
- 增加旧证据的版本边界和重新核验规则；
- 增加阶段门禁复核人、日期、结论和阻塞项；
- 增加 P0-REA 的覆盖标准，明确不要求对大型 Bundle 做无边界的全量语义图；
- 增加制品 tag/digest、Pod imageID、运行环境和 Evidence ID 的追踪要求；
- 增加 `阻塞` 状态，避免把缺少旧源码或环境条件误记为普通“分析中”。

## 5. 后续执行规则

1. 先补 P0-REA 文档和证据，不修改模块功能代码。
2. P0-REA 复核通过后，补 P1-REA 公共行为矩阵。
3. P1-REA 复核通过后，逐模块完成 P2-REA。
4. P2-REA 复核通过前，不继续 ConfigMap、Secret、ServiceAccount 的正式开发，不创建后续模块短期分支。
5. P2-REA 通过后，重新划分正式 P2-DEV 的提交边界；历史先行提交保留，但不能直接视为正式验收。
6. 每次代码、制品或部署版本变化，都重新核对受影响证据。
7. 只有部署制品身份可回读、rollout 成功、Playwright 在实际 Pod 上通过，才能完成 Pn-VERIFY。
8. 所有高风险未知项、证据冲突或环境阻塞都必须在矩阵中显式记录，不以“代码已经能运行”关闭。
