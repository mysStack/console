# V3→V4 范围决策：全量迁移 vs 只迁移影响使用的部分（2026-10-28）

> 基线：`release-4.1.5` @ `8954c6595`（已包含 V3 桥接修复）。
> 本文用 REA 逆向取证作为辅助，**不做代码改动**；结论只决定“迁移范围”，不代替业务取舍。

## 1. 要回答的问题

| 选项                 | 含义                                                              |
| -------------------- | ----------------------------------------------------------------- |
| **A 全量迁移**       | 把 138 个 V3 嵌入页面全部改写成 V4 原生实现，最终移除 `consolev3` |
| **B 影响使用的部分** | 只改写“业务必须改、且宿主桥接解决不了”的页面，其余保持 V3 嵌入    |

## 2. 判据：能做 ≠ 需要做

两个维度必须分开，不能用一个维度决定：

- **能做**（技术可行性）：修复点能否只落在宿主桥接层（`ConsoleV3ResourceList`、`useV3Actions`、Wujie 封装），不改 V3 内部。
- **需要做**（业务必要性）：该页面在生产的使用频率 × 出错后果，由业务方填写，工程侧不代填。

|                              | 需要做                            | 不需要做         |
| ---------------------------- | --------------------------------- | ---------------- |
| **能做**                     | 修桥接层，成本最低                | 保持现状         |
| **不能做**（必须改 V3 内部） | **定向 V4 重写 ← 这才是迁移范围** | 不处理，记录风险 |
| **未知**                     | 先验证再定级                      | 暂不投入         |

## 5. 两个选项对比

> 成本为**粗估**，需在范围确定后重估；不作为承诺。

| 维度       | A 全量迁移                                          | B 影响使用                                 |
| ---------- | --------------------------------------------------- | ------------------------------------------ |
| 范围       | 138 个页面全部重写                                  | 仅“需要做 ∩ 不能做”                        |
| 粗估工作量 | 100+ 页面 × 2–5 人天                                | 预计 10–30 人天（取决于交集大小）          |
| 主要风险   | 行为差异、字段/权限对齐、测试矩阵爆炸、并行开发冲突 | 桥接层依赖 wujie 私有字段；V3 行为仍是黑盒 |
| 收益       | 彻底移除 V3，长期可控                               | 快速稳定，成本低；V3 债务保留              |
| 前提       | 需要完整 REA + 逐页验收                             | 需要可靠盘点 + 业务分级                    |

## 6.4 扩展初始化报错定性（2026-10-29）

补充取证后可以定位这些报错的来源：

- 全部报错发生在**页面加载时**，不是终端点击时；宿主捕获并打印在 `/dist/js/main.12d681a0.js:7376`，扩展代码以 `<anonymous>` 字符串求值。
- 受影响的扩展入口共 7 个：
  - `getExtensionConsoleV3Embed is not a function`：`ks-autoscaling`、`kubeeye`、`frontend-forge`、`openkruise`、`whizard-telemetry`
  - `ConfigConstants.SIDER_COLLAPSED` 解构失败：`metrics-server`、`vertical-pod-autoscaler`
  - `getStoreWithQueryHooks` 不存在：`ingress-utils`
- 在本仓库源码与 `node_modules` 中均搜不到 `getExtensionConsoleV3Embed` 的定义；`git log -S` 只命中文档提交，从未有过该导出。
- 当前部署制品就是 `release-4.1.5` 树，本评估分支只有文档改动。

结论：**扩展侧期望的宿主 API 在该 console 版本中不存在，属扩展与宿主版本不匹配**，与 V3 桥接和本次评估无关；
它会让扩展页面初始化失败（`/whizard-telemetry` 整页空白即属此类）。处理方向是对齐扩展版本或补宿主 API，不应计入 V3→V4 重写范围。

## 7. 建议

**选 B**，但需要三个前置条件：

1. 业务填完“需要做”（A 高频核心 / B 偶尔 / C 基本不用）。
2. 工程可行性验证：39 个“未知”页中，除联邦项目（无环境）和 5 个未安装组件页外，已完成逐页验证；容器日志与新标签页终端均可用（§6.1–§6.3）。
3. 交叉得到重写清单，按页面验收，不再按模块整批迁移。

**不建议现在选 A**：138 个页面里已有 99 个被证明可由宿主桥接覆盖，全量重写会把已解决的问题重新做一遍，
并引入新的行为差异风险；且 V3 不可重建，重写期间新旧实现需长期并存，成本被低估。

### 7.1 若选 B：候选重写清单（工程视角，待业务分级）

按“宿主桥接解决不了”筛完后，**没有任何一个页面因“渲染/列表/日志/终端”本身必须重写**；剩余候选只有三类：

| 缺陷                                              | 影响范围         | 为什么不能只改宿主        | 处理方式                           |
| ------------------------------------------------- | ---------------- | ------------------------- | ---------------------------------- |
| R7 跨项目切换约 2.3 s 重引导（有加载态）          | 全部项目级 V3 页 | V3 ProjectLayout 内部行为 | 业务判为高频才重写对应项目级页面   |
| R5 `destroy()` 竞态报错（`null._cacheListeners`） | 全部共享实例     | wujie 1.0.25 内部         | 升级/打补丁 wujie，不需要页面重写  |
| 扩展初始化报错（§6.4）                            | 扩展页面         | 扩展与宿主版本不匹配      | 对齐扩展版本或补宿主 API，不属迁移 |

也就是说，B 方案的重写清单规模主要由“业务认为 R7 是否可接受”决定，而不是由 138 个页面的数量决定。
